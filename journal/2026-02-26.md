# 2026-02-26 - Created Meal Planning Agent Pipeline

## User Request

The user requested the creation of 3 custom Claude Code agents for the recipe vault:
1. **Maitre** (orchestrator): gathers user requirements (people count, meal type, cook time, dietary) and coordinates the pipeline.
2. **Chef** (meal planner): plans meals using existing vault recipes and creates new ones, saves meal plans to vault.
3. **Shopping Assistant** (price hunter): looks up ingredient prices at Aldi, Coles, Woolworths and produces optimized shopping lists with two strategies (split shopping vs single supermarket).

Key user decisions during clarification:
- Chef should be able to create new recipes (not just select from existing).
- Shopping assistant should use WebFetch for live price lookups.
- Output should be saved to vault as Obsidian-compatible `.md` files.
- Agents must be able to call each other (maitre orchestrates via Task tool).

## Reasoning

The PM agent assessed this as a complex task due to inter-agent coordination, domain-specific logic, and external data source integration. Three clarifying questions were asked (chef scope, web access strategy, output format).

The Plan agent designed a pipeline where the maitre spawns the chef via the Task tool, receives the meal plan path, then spawns the shopping assistant. The plan evaluator flagged 7 improvements: explicit Requirements Brief schema, `plans/` directory creation, frontmatter inconsistency handling, WebFetch reliability concerns, ingredient file creation conventions, and output format specificity. All were addressed in the revised plan.

The build evaluator passed with 3 minor recommendations: add rejection path in maitre, consider splitting chef scope for large plans, and remove hardcoded paths. The first and third were implemented.

## Accepted Solution

Three agent files in `.claude/agents/`:

- **`maitre.md`**: Uses `AskUserQuestion` for 4 questions with defaults, `Glob` to count vault recipes, `Task` to spawn chef then shopping-assistant. Includes rejection/edit loop for requirements confirmation.
- **`chef.md`**: Inventories existing recipes (handles both YAML frontmatter and inline `::` metadata), plans meals with 6 prioritized goals (dietary compliance > nutrients > waste minimization > time > diversity > base+variations), creates new recipes/ingredients following vault templates, saves to `plans/YYYY-WNN/meal-plan.md`.
- **`shopping-assistant.md`**: Three-tier WebFetch strategy (Frugl aggregator > Google/DuckDuckGo > direct supermarket sites), best-effort price lookup with graceful degradation, dual strategy output (split vs single supermarket), saves to `plans/YYYY-WNN/shopping-list.md`.

### Cross-File Relationships

- **maitre.md -> chef.md**: Maitre produces a structured Requirements Brief that the chef parses as input. The format is explicitly defined in both agent prompts.
- **chef.md -> shopping-assistant.md**: Chef produces a meal plan with an `## Ingredient Summary` section that the shopping assistant parses for price lookup.
- **chef.md -> `_meta_/_templates_/Recipe.md`**: Chef follows this template when creating new recipes, ensuring vault consistency.
- **chef.md -> `_meta_/_templates_/Ingredient.md`**: Chef follows this template when creating new ingredient files.
- **shopping-assistant.md -> `.claude/settings.local.json`**: Shopping assistant's WebFetch targets are constrained by the permitted domains in settings.
